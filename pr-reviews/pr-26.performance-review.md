# Performance Review: PR 26 - Multi-page HTML report restructure

**Reviewed:** 2026-08-24  
**Reviewer:** performance-specialist  
**PR:** feat/multipage-report → main  
**Scope:** Report generation (not hot-path code)

## Summary

This PR converts a single-page HTML report to a multi-page layout. The refactor is generally sound for a non-hot-path component. The main performance change is trading one large file write for N smaller writes plus asset copying, which is appropriate for improved browser UX. No significant performance concerns identified, with two minor optimization opportunities noted.

## Findings

### Finding 1: Redundant Jinja2 Environment creation
**Severity:** low  
**Location:** build.py:1619-1622  
**Issue:** Creates a fresh `Environment` and `FileSystemLoader` for each report build, despite templates being static.  
**Recommendation:** Move environment creation to class-level (e.g., `_template_env` cached property or class variable). The old `_render_html` had the same pattern, so this is not a regression.  
**Estimated impact:** ~5-10ms saved per report (negligible for typical workflow)  
**Patch:**
```python
# At class level, add cached property:
@functools.cached_property
def _template_env(self) -> Environment:
    """Cached Jinja2 environment for template rendering."""
    return Environment(
        loader=FileSystemLoader(str(_TEMPLATE_DIR)),
        autoescape=True,
    )

# In _render_multi_page_html:
def _render_multi_page_html(self, outdir: Path, sections: list[_Section]) -> list[Path]:
    env = self._template_env  # Use cached instance
    # ... rest unchanged
```

### Finding 2: N-file writes vs single-file write overhead
**Severity:** low  
**Location:** build.py:1708  
**Issue:** Writing N HTML files (1 per section, ~10-15 typical) vs 1 large file. Each `write_text()` call incurs syscall overhead.  
**Recommendation:** No action needed. The browser performance win (smaller page loads, faster navigation) far outweighs the ~10-20ms file I/O overhead. For very large reports (100+ sections), consider buffering writes or using `open().write()` for slight efficiency gains.  
**Estimated impact:** ~1-2ms per file write on modern SSDs; total <30ms for typical 10-section report  

### Finding 3: Asset copying uses `shutil.copy2` (preserves metadata)
**Severity:** low  
**Location:** build.py:1612-1613  
**Issue:** `shutil.copy2` preserves file metadata (mtime, mode), which is unnecessary for generated reports. `shutil.copyfile` would be marginally faster.  
**Recommendation:** Optional micro-optimization. Replace `copy2` with `copyfile` if metadata preservation is not required. Realistically saves <1ms per file.  
**Estimated impact:** <2ms total (2 files × <1ms)  

## Non-Issues (Explicitly Verified)

- **Template inheritance overhead:** Jinja2 template inheritance (`{% extends "base.html.j2" %}`) has negligible overhead (~0.1ms per render). The base template is small and rendering is not in a hot loop.
- **Navigation data duplication:** The `all_sections_for_nav` list is reconstructed once and shared across all page renders. No N² behavior detected.
- **Section-to-dict conversion:** The dict comprehension for `section_dict` (lines 1643-1659) is simple field copying with no heavy computation. Expected cost: <1ms per section.
- **Memory usage:** Writing N files vs 1 file has no material memory impact. Each page renders independently with bounded template context (~few KB per section dict).

## Browser Performance Implications (Out of Scope)

The multi-page design improves browser performance for large reports:
- **Single-page baseline:** 1-3 MB HTML + inline CSS/JS loaded upfront
- **Multi-page refactor:** ~50-150 KB per page, external assets cached

This is a UX win and appropriate trade-off for the ~20-30ms file I/O overhead introduced.

## Recommendations Summary

1. **Optional:** Cache Jinja2 environment as class property (Finding 1)
2. **No action:** N-file write overhead is acceptable for this use case (Finding 2)
3. **Optional:** Use `shutil.copyfile` instead of `copy2` for minor speedup (Finding 3)

None of these are blocking. The refactor is performance-neutral to slightly positive overall when accounting for browser-side benefits.
