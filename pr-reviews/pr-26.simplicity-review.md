# Simplicity Review: PR 26 - Multi-page HTML Report Restructuring

Reviewed: 2026-08-24
Reviewer: simplicity-reviewer

## Summary

This PR successfully converts a single-page HTML report to a multi-page layout with navigation, but introduces significant duplication and complexity that could be avoided. The most critical issue is that **both** the old `_render_html` method and the new `_render_multi_page_html` method are kept, with duplicated summary statistics generation logic (30+ lines). The section content rendering is duplicated across `single_page.html.j2` (lines 71-205) and `_section_content.html.j2` (lines 186-326) — a 142-line block of nearly identical Jinja2 code. The template inheritance pattern (`base.html.j2` → `section.html.j2`) is reasonable for multi-page output, but the retention of the entire single-page rendering path suggests scope creep or incomplete migration.

Diff size: 255 additions / 3 deletions across 7 files.
Reduction estimate (best-case if all suggestions applied): ~180 LOC (70% reduction in added code).

### Finding 3: Duplicated summary statistics generation
**Severity:** suggested
**Category:** duplication
**Location:**
- `build.py:1604-1627` (in old `_render_html`)
- `build.py:1646-1669` (in new `_render_multi_page_html`)
**Issue:** The summary statistics calculation (total_figures, total_errors, total_warnings, status determination with thresholds) is duplicated across both rendering methods. 24 lines of identical logic including the error threshold of 5, warning messages, and status strings.
**Recommendation:** Extract to a private helper `_compute_summary_stats(self, sections: list[_Section]) -> dict` and call from both methods (or just the new one if the old method is removed per Finding 1).
**Patch:**
```python
def _compute_summary_stats(self, sections: list[_Section]) -> dict:
    """Compute summary statistics for report landing page."""
    total_figures = sum(
        len(s.figures) + sum(len(sub.figures) for sub in s.subsections)
        for s in sections
    )
    total_errors = len(self._errors)
    total_warnings = len(self._warnings)
    
    if total_errors > 5:
        status = "error"
        status_message = f"{total_errors} errors encountered"
    elif total_errors > 0:
        status = "warning"
        status_message = f"{total_errors} errors, report partially complete"
    elif total_warnings > 0:
        status = "warning"
        status_message = f"{total_warnings} warnings"
    else:
        status = "success"
        status_message = "All sections generated successfully"
    
    return {
        "total_sections": len(sections),
        "total_figures": total_figures,
        "total_errors": total_errors,
        "total_warnings": total_warnings,
        "status": status,
        "status_message": status_message,
    }

# Then in _render_multi_page_html:
summary = self._compute_summary_stats(sections)
```

## Severity calibration notes

- **Blocking** items (Findings 1, 2) introduce dead code and 135+ lines of duplicated template logic that will be harder to maintain long-term. These should be addressed before merge.
- **Suggested** items (Findings 3, 4, 6) reduce duplication and clarify scope but don't fundamentally undermine the refactor. Addressing them improves code quality significantly.
- **Nit** items (Findings 5, 7, 8, 9, 10) are minor cleanups. The most impactful is Finding 5 (over-engineered filename assignment), which simplifies the design.

## Overall assessment

The PR achieves its goal (multi-page HTML output with navigation), but the implementation is **too large and carries too much baggage**. With the old rendering path removed (Finding 1) and template duplication eliminated (Finding 2), the diff could shrink from 255 LOC to ~75 LOC — a much more reviewable and maintainable change. The `lnd_in` file reading feature (Finding 6) should be split into a separate PR. The template inheritance pattern (`base.html.j2` + `section.html.j2`) is appropriate for the multi-page design and not over-engineered; the problem is the retention of the entire single-page path and the failure to DRY the section content rendering block.

**Recommendation:** Request revisions to address Findings 1, 2, and 6 (blocking/scope creep) before approval. Findings 3, 4, and 5 are worth addressing but not strictly blocking.
